# Hermes Python temporary runtime capture verification

## Scope

The new capture API copies the selected CPython base, complete site-packages tree,
declared editable modules/packages and sibling resource directories into a private
temporary tree. It recognizes the installed editable finder without executing it,
replaces recognized startup behavior with a fixed staged-path bootstrap, and binds
the copied metadata and generated bytes into a deterministic manifest identity.

Windows creates the runtime directory with a protected, inheritable current-user
DACL at creation. A restrictive directory handle and retained ancestor handles
exclude root write handles and movement while the capture is alive. Existing general
filesystem share policy is unchanged. Unix uses a private temporary parent.

This is a temporary capture, not durable approval or an operating-system sandbox.
Dropping its owner removes it. Future durable promotion must flush file contents and
publish directories/manifest durably before sealing approval. No production command
or recovery path consumes this API yet. No harness version is promoted to Full.

## Installed capture evidence

The explicit installation is the existing Hermes 0.17.0 Windows editable venv at
`C:\Users\User\AppData\Local\hermes\hermes-agent\venv\Scripts\hermes.exe`.
The check reads that installation and executes only a fixed path probe using copied
CPython. It does not execute the original launcher, import Hermes, or run a Hermes
management command. Its environment, current directory, HOME and HERMES_HOME are
synthetic. A Windows Job Object owns the child and a 15-second deadline bounds it.

The earlier runs captured 14,629 files, 2,452 directories and 342,033,097 bytes.
The copied interpreter reported isolated/no-site mode, no loaded site module and
only staged search paths despite deliberately supplied PYTHONPATH/PYTHONHOME.
A synthetic sitecustomize canary did not run and post-probe inventory verification
passed. The original installation and ordinary harness state were not modified.

Initial debug capture took 693.80 seconds. Removing a redundant full stage scan and
using an equivalent ASCII collision fast path reduced it to 396.84 seconds (copy
203.67 seconds; copy plus source recheck 337.17 seconds). These are local debug-build
measurements, not a release performance claim. The final pin/disk-flush rerun passed:
same inventory and startup assertions, 681.53 seconds for capture and 817.89 seconds
for the complete test, while migration/sync regressions were running concurrently.
This verifies correctness; capture speed and frontend progress/cancellation still
need qualification before exposing this path in setup.
