# Hermes runtime approval verification

Native plans now preserve a distinct versioned retained-runtime reference through
approval hashing, sealing and reversible reopening. The portable identity keeps
Windows retention operations in their existing module. Production constructors
still have no runtime binding; retained Python execution is the next integration.

Approval v1 rejects retained bindings. Approval v2 keeps the exact prior three/four
member preimages when absent; a present binding adds an explicit native-memory
member followed by the tagged runtime member. Changed identity/key, unsupported
schema/kind, wrong harness/platform and removing the binding fail validation or
approval verification. Older sealed output omits the field and reopens as None.

Legacy hashes were generated by temporarily running the committed c48965d approval
implementation and restoring the working implementation byte-for-byte in finally.
The test freezes both empty and nonempty native-memory cases, rather than deriving
its expectations from the implementation under test.

Execution checks stop an unconsumed binding before engine journal acquisition,
production launcher discovery, or watch-only harness verification. The engine
regression first failed because the default adapter reached journal acquisition.
Native file compensation still does not require Python; recovery identities remain
readable, and existing Hermes CLI recovery remains unsupported.
