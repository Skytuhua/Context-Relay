# Transactional MCP Adapter Installation Design

## Status

Approved implementation correction for Task 8 of
`2026-07-30-mcp-memory-tasks-handoffs.md`.

## Problem

The scoped MCP bridge design requires Claude Code, Codex, and Hermes
registrations to flow through semantic preview, explicit active approval,
apply-time digest revalidation, effective-state validation, compensation, and
rollback.

The adapter layer already imports, renders, classifies, and validates
declarations, and the native transaction engine safely applies file
mutations. Two assumed production layers are absent:

1. `HarnessPreview`, `HarnessApply`, and `HarnessRollback` have protocol and
   local-IPC shapes but are routed to `HarnessUnsupported`; no production
   service builds or persists `SetupPlan`.
2. `SetupPlan.cli_operations` is approval-hashed but has no executor, WAL, or
   compensation path. The native transaction engine applies only
   `ApprovedMutation` file objects.

Adapter fixture tests alone cannot satisfy installation acceptance. Directly
editing Claude/Codex configuration would bypass their supported CLI surfaces,
and directly running rendered test commands would bypass approved transaction
and recovery state.

## Decision

Insert a transactional adapter-setup prerequisite before Task 8 acceptance.
Land canonical bridge components and pure adapter rendering first, then add a
narrow approval-bound CLI transaction path for the managed
`context-relay` MCP declaration.

The implementation remains deliberately narrow:

- Claude Code and Codex use only their existing official MCP add/remove and
  list/get surfaces.
- Hermes continues to use the reviewed native YAML transaction.
- CLI mutation support accepts only the stable global `context-relay` MCP
  declaration generated by `core::mcp::install`.
- Arbitrary adapter CLI operations, package installation, explicit preview
  rejection state, and general configuration takeover are non-goals.

## Canonical Bridge Declaration

`core::mcp::install::bridge_component` produces one harness-specific stable
record:

- name `context-relay`;
- kind `McpServer`;
- global scope;
- absolute regular non-link executable;
- arguments `["--harness", "<claude-code|codex|hermes>"]`;
- no environment, credential, URL, project, or working-directory field;
- `provenance.harness = None`;
- Hermes metadata location
  `config:mcp_servers.context-relay`.

Unix executables require at least one execute bit. Native paths must be
losslessly representable by the adapter's JSON/YAML surface; lossy conversion
is rejected. The stable record ID is different for each harness.

Hermes receives a narrowly gated authority exception for exactly that stable
record, name, scope, kind, structural location, and canonical secret-free
body. General Hermes profile/provenance authority rules remain unchanged.

## Internal CLI Mutation Model

`NativeTransactionPlan` gains:

```rust
pub struct CanonicalCliDeclaration {
    pub harness: HarnessId,
    pub server_name: String,
    pub canonical_body: String,
    pub fingerprint: Sha256Digest,
}

pub struct ApprovedCliMutation {
    pub stable_id: String,
    pub expected: Option<CanonicalCliDeclaration>,
    pub intended: Option<CanonicalCliDeclaration>,
    pub forward: Vec<CliOperation>,
    pub rollback: Vec<CliOperation>,
}
```

Only Claude Code and Codex bridge plans contain CLI mutations. Hermes bridge
plans contain native file mutations and an empty CLI mutation list.

The expected declaration is either absence or an exact, canonical,
secret-free declaration. Preview refuses to take over a redacted,
secret-bearing, malformed, or unmanaged same-name declaration. The intended
declaration is likewise canonical. Forward and rollback operations are
generated by the adapter; callers never supply them.

## Approval Binding

New bridge plans use `approval_hash_v2` with a distinct domain separator. It
binds:

- the complete existing v1 plan preimage;
- ordered CLI stable IDs and harness/server targets;
- expected and intended declarations and fingerprints;
- ordered forward and rollback operations.

Validation rejects duplicate stable IDs or targets, mismatched fingerprints,
operations using a different executable than the attested harness executable,
unsupported timeouts, and any flattening mismatch between
`SetupPlan.cli_operations` and the internal forward operation list.

`approval_hash_v1` remains available for legacy file-only plan tests and
interrupted legacy recovery. A sealed plan envelope records explicit schema
and approval versions; a v2 CLI plan is never interpreted as v1.

The bridge executable digest is stored in
`SetupPlan.expected_native_digests`, separate from the harness executable
digest, and is rechecked before any mutation.

## Preview and Plan Lifecycle

`BridgeInstallService::preview`:

1. Locates and attests the bridge executable.
2. Probes and imports the selected harness.
3. Constructs the canonical bridge component.
4. Derives expected and intended declarations.
5. Renders, diffs, and classifies through `HarnessAdapter`.
6. Derives `ApprovalClass::Active` for bridge create, update, enable,
   disable, or remove; callers cannot downgrade it.
7. Generates forward and rollback operations.
8. Builds the full native plan and computes approval v2.
9. Persists the sealed canonical plan as `previewed`.
10. Returns the public `SetupPlan` without writing harness state.

Declining a preview means not sending `HarnessApply`; preview itself performs
no configuration or harness CLI mutation. No public protocol addition is
required.

Plan lifecycle states are persisted and compare-and-swapped:

```text
previewed -> applying -> applied
                     \-> apply_restored | conflict
applied   -> rolling_back -> rolled_back
                         \-> rollback_restored | conflict
previewed -> expired
```

Apply and rollback replay are idempotent. Rollback derives a new internal plan
whose expected/intended declarations and forward/rollback operations are the
exact inverse of the original plan, while public `HarnessRollback` continues
to name the original plan ID.

## CLI Transaction Execution

Adapters implement a narrow `NativeCliExecutor`:

```rust
pub trait NativeCliExecutor {
    fn compare_cli_targets(
        &mut self,
        mutations: &[ApprovedCliMutation],
    ) -> Result<(), BoundaryError>;

    fn apply_cli_mutation(
        &mut self,
        mutation: &ApprovedCliMutation,
    ) -> Result<CliMutationOutcome, BoundaryError>;

    fn restore_cli_mutation_if_matches(
        &mut self,
        mutation: &ApprovedCliMutation,
    ) -> Result<CliRestoreOutcome, BoundaryError>;

    fn finish_committed_cli_mutations(
        &mut self,
        mutations: &[ApprovedCliMutation],
    ) -> Result<(), BoundaryError>;
}
```

It executes only adapter-generated operations using the attested harness
executable. It never invokes the configured MCP bridge. Effective validation
uses only existing non-starting list/get or config-inspection surfaces.

The existing top-level native transaction step numbers remain stable. CLI
mutation work is a WAL-backed subphase of step 17 after activation-reference
file writes:

1. Reprobe and compare file targets and CLI declarations.
2. Apply file payload and disabled-executable mutations.
3. Apply activation references.
4. Prepare each CLI WAL row before running its command.
5. Run one approved forward operation sequence.
6. Reprobe the declaration and require the intended fingerprint.
7. Mark the CLI row applied.
8. Validate effective configuration.
9. Commit ownership and receipt.

Compensation reverses application order: CLI mutations in reverse sequence,
then file/native mutations. A restore occurs only while live state still
matches the approved intended fingerprint. Divergence is a conflict and is
never overwritten.

An uncertain command outcome is resolved by probing:

- expected state: no mutation committed;
- intended state: mark applied, then compensate;
- any other state: conflict.

## Durability and Recovery

Schema v9 adds:

- setup-plan lifecycle state linked to the existing encrypted `native_plans`
  payload;
- `native_cli_wal` rows containing canonical expected/intended declaration
  bytes, fingerprints, forward/rollback operation bytes, and state.

CLI WAL states are:

```text
prepared -> applied -> restore_prepared -> restored
       \---------------------------------> conflict
```

Startup recovery processes CLI WAL before file WAL for pending/restoring
transactions and verifies CLI cleanup before native cleanup for committed
transactions. `prepared` rows are probed to distinguish no write from an
uncheckpointed applied write. `restore_prepared` may retry only while live
state still equals the approved intended declaration.

A no-op CLI recovery implementation is allowed only when the transaction has
no CLI rows; it must fail closed otherwise.

## Adapter Behavior

Claude Code:

- forward: `mcp add-json context-relay <canonical-json> --scope user`;
- rollback/removal: official user-scope MCP remove or exact prior declaration;
- validation includes global `.claude.json` MCP names and uses list/get only.

Codex:

- forward: `mcp add context-relay -- <bridge> --harness codex`;
- rollback/removal: official MCP remove or exact prior declaration;
- validation uses plugin list and MCP list/get only.

Hermes:

- no CLI mutation;
- exact YAML projection under `mcp_servers.context-relay`;
- existing native before-image and rollback machinery;
- active gateway-idle gate remains required.

All adapters recheck the harness executable and bridge executable digests
before mutation, accept only the exact managed target, and reject a
secret-bearing prior declaration.

## Daemon Routing

Production locates `context-relay-context-mcp` beside `contextd`, with an
injectable locator for tests. The public IPC shape remains:

```text
HarnessPreview(HarnessParams)  -> LocalResult::Plan
HarnessApply(PlanParams)       -> LocalResult::Empty
HarnessRollback(PlanParams)    -> LocalResult::Empty
```

These operations use the daemon's ordered workspace path. `HarnessRepair`
remains outside this task. Startup recovery receives the production CLI
recovery implementation.

## Acceptance

The prerequisite is complete only when tests prove:

- exact Claude, Codex, and Hermes declarations;
- active classification for every bridge-changing class;
- bridge digest change between preview and apply causes no harness write;
- a declined preview causes no harness write;
- validation never starts the bridge;
- apply failure restores exact prior state;
- crashes around command/checkpoint boundaries recover deterministically;
- rollback restores absence or exact prior canonical declaration;
- live divergence produces conflict without overwrite;
- apply and rollback replay are idempotent;
- public daemon preview/apply/rollback succeeds.
